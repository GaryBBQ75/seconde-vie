# Seconde Vie · Gestion de ressourcerie

Application hébergée : https://seconde-vie-atelier.gary-legrill.chatgpt.site/.
Démonstration fictive et locale : https://seconde-vie-atelier.gary-legrill.chatgpt.site/?demo=1.

Voir [le périmètre du socle et des modules](CORE.md) pour les fonctions, les accès et les limites.

## Développement

Node.js 24 ou supérieur : `npm ci`, `npm test`, `npm run dev` et `npm run build`.
Ouvrir http://localhost:4173. Le simulateur SQLite conserve ses données dans `.local/`, ignoré par Git. Son identité fictive est injectée uniquement par le serveur de développement. Le Worker de production utilise l’identité fournie par Sites et les autorisations serveur.

La construction regroupe le Worker en un module ESM et copie les ressources client. `.openai/hosting.json` déclare D1 (`DB`) et R2 (`BUCKET`). Les migrations SQL versionnées de `drizzle/` s’appliquent à la publication.

`public/domain.js` contient les règles communes ; `public/demo-api.js` les adapte au stockage local de la démonstration ; `worker/core.mjs` les applique aux données partagées. Les photos sont servies par une route protégée par structure.

La V1 vise les ressourceries et recycleries. Réception des dons, donateurs, tri, stock, étiquettes et suivi des flux font partie du socle. Atelier, collectes, planning, caisse et sélection pour la vitrine sont activables séparément. Les champs de réception, les provenances et les formats se règlent dans l’application ; catégories et emplacements se règlent par site. Le relais en caisse attribue les ventes sans être une nouvelle authentification du terminal. Les connecteurs e-commerce restent à qualifier ; achat-revente et dépôt-vente sont hors périmètre de la V1.

Les sauvegardes JSON portent sur l’espace courant. Une restauration conserve les comptes et leurs droits, et crée une version récupérable des données précédentes. Les photos restent dans R2 : le JSON n’est pas une archive autonome des images.

Les clés facultatives de recherche restent dans l’environnement serveur. Leurs noms sont documentés dans `.env.example`. Les bibliothèques de scan, OCR et reconnaissance locale, leurs modèles et licences sont dans `public/vendor/`. Les six ressources tierces volumineuses sont restaurées par `npm run build` à partir des adresses publiques versionnées dans `scripts/vendor-assets.json`, avec vérification SHA-256. Pour lancer le développement depuis un clone GitHub vierge, exécuter d’abord `node --use-env-proxy scripts/vendor-assets.mjs`. Les ressources sont ensuite servies localement par l’application. Une saisie manuelle reste disponible.

Dans GitHub, cette application reste dans `demo/` pour préserver l’historique et le serveur PostgreSQL initial à la racine. Ses API sont indépendantes.

## Finalisation de la V1

La caisse interne comprend ouverture par site, fond initial, mouvements d’espèces, comptage et clôture, annulation/remboursement intégral tracé et retour au contrôle. Les modules Devis et factures et Adhésions et cotisations se règlent séparément. Le rôle Administration est distinct de la caisse. L’import CSV de stock appartient au socle et nécessite le rôle Responsable.

Les documents émis sont figés et numérotés ; les règlements sont enregistrés sans déclencher de paiement externe. Les rapports calculent les recettes nettes après remboursements. Les journaux financiers ne peuvent pas être réécrits par une restauration. Les limites fiscales, les conditions de reprise et les fonctions hors périmètre sont détaillées dans `CORE.md`.

## Planning et tests sans mot de passe

Ouvrir `/?demo=1#planning` et choisir un profil fictif, sans code ni mot de passe. Le responsable prépare, copie et publie les semaines ; les membres confirment leurs créneaux et déclarent leurs disponibilités. Le rôle Coordination du planning délègue la gestion sans ouvrir l’administration des comptes. Les données de cette démonstration restent locales au navigateur ; l’espace partagé garde son identité et ses droits serveur.

## Agenda interactif

Le responsable utilise un agenda horaire en vue semaine ou jour : glisser un nom pour créer un brouillon, déplacer une affectation et tirer sa poignée pour ajuster la durée. La sélection d’un nom suivie d’un clic dans l’agenda et le formulaire offrent une alternative au glissement. Les conflits entre sites et les indisponibilités sont contrôlés côté interface et serveur ; un refus d’enregistrement restaure l’affichage. Les membres consultent leur agenda publié, sans commandes de déplacement.

Le composant standard FullCalendar 7.1.4 est issu de son dépôt officiel (licence MIT), sans extension payante. `browser/planning-vendor.js` et `scripts/build-calendar.mjs` génèrent les ressources JavaScript, CSS et licences à partir des versions verrouillées dans `package-lock.json`, au lancement du développement et à la construction. Ces sorties sont ignorées dans Git. Les heures restent exprimées dans le fuseau de la structure.

## Identification photo et estimation d’occasion

Dans Réception, trois onglets permettent de commencer par un code-barres, des photos + IA ou une saisie manuelle. Scanner reste consacré à retrouver une fiche existante ; la Réception est la page de départ sur mobile aussi. L’onglet Photos + IA permet de préparer une série de une à six vues du même objet, avec suppression individuelle. La caméra occupe tout le viewport mobile ou tablette et reste ouverte pour des prises successives. Choix avant/arrière ou objectif, zoom matériel si pris en charge (sinon recadrage numérique également appliqué à la photo), mise au point continue et éclairage selon les capacités du matériel. Chaque miniature peut être supprimée. L’import accepte plusieurs fichiers. Aucun appel d’analyse ne part à l’ajout ou à la suppression d’une vue : le bouton Analyser lance explicitement le modèle multimodal `google/gemini-2.5-flash` via `/v3/chat/completions`. `EDENAI_VISION_MODEL` permet de choisir un autre modèle compatible ; `EDENAI_API_KEY` et l’ancien nom de secret `Eden AI` sont tous deux reconnus. Les propositions restent à confirmer et leurs champs sont corrigeables. Les champs du schéma de la catégorie sont transmis au modèle : couleur, coupe et fermeture pour le textile, numéro de série et tension pour l’électrique, etc. La description et une proposition d’état visuel apparaissent dans le formulaire. Taille, composition, numéros et valeurs techniques nécessitent des inscriptions lisibles ; une hypothèse visuelle est distinguée d’un champ observé. L’analyse locale du type d’objet et la saisie manuelle restent disponibles.

Comparer les prix d’occasion utilise la recherche Google de SerpAPI lorsque `SERPAPI_API_KEY` est configurée, sinon `web/search/linkup` via Eden AI. Les prix EUR structurés des extraits Google sont conservés ; aucune réponse de synthèse ou valeur inventée n’est utilisée. La recherche est formulée avec le type, la marque et le modèle fiable, ainsi que le code comme alternative lorsqu’il est disponible. Les montants sont lus dans les extraits sourcés, sans prix inventé par le modèle d’identification. Référence, état et accessoires doivent être vérifiés. Produits neufs, accessoires seuls, lots et pages de résultats sont exclus du calcul. Un montant absent ou ambigu peut être relevé manuellement après consultation du lien. La comparaison de prix concerne actuellement la France en EUR ; l’identification reste disponible pour les autres devises.

Une estimation provisoire peut être préparée dès deux annonces comparables avec un prix effectivement trouvé. Avec seulement deux annonces, un état d’annonce non précisé ou un état produit inconnu, le résultat porte une réserve explicite. La confirmation d’un repère sans mode provisoire exige toujours trois annonces. Le repère de prix bas est le quartile inférieur empirique, puis une remise ressourcerie réglable de 0 à 50 % est appliquée (20 % proposés initialement, préférence conservée sur ce poste par site). Cette règle est un choix de tarification, pas une valeur de marché garantie. Les prix sont ceux demandés par les vendeurs, hors livraison, et non des ventes réalisées. La recherche des prix est distincte de l’identification et ne part qu’au clic sur Rechercher un prix. Elle est aussi accessible depuis une réception par code-barres ou saisie manuelle. La proposition de prix peut être préparée avant confirmation, est préremplie et reste modifiable ; l’utilisateur peut enregistrer sans prix. Pour un appareil non testé, le prix potentiel est conditionné à la confirmation du fonctionnement. Les appareils déclarés non fonctionnels utilisent les offres pour pièces. Le retrait d’un comparable ou une modification de la règle recalcule la proposition automatique. Un prix saisi manuellement reste sous le contrôle de l’opérateur. Les premiers liens consultés et la règle appliquée sont proposés dans la note de la fiche.

Les photos partent vers Eden AI uniquement après un clic sur Analyser. Les étapes Identification, Recherche du prix et Fiche prête sont affichées sans pourcentage fictif ; une erreur conserve les vues et les champs pour réessayer. Le prix proposé et son niveau de fiabilité figurent en tête du résultat ; deux annonces exploitables permettent un repère provisoire, avec ses limites affichées. La conservation sur la fiche reste facultative et limitée aux trois premières vues, annoncée à côté de la case. L’onglet Code-barres de Réception conserve les catalogues et le lecteur de codes. Les références catalogue préparent la saisie manuelle ; la recherche web des prix reste facultative. La clé reste au serveur. L’API exige une session Sites, une origine identique et un identifiant de requête ; une réutilisation de la même requête est mise en cache pendant cinq minutes en mémoire. La limitation de fréquence et cette déduplication sont locales à l’instance Worker et ne constituent pas un plafond global de dépenses. Les photos ne sont pas enregistrées dans D1 par l’assistant.

Validation du développement : tests du contrat API avec fournisseurs simulés et parcours navigateur sur données explicitement fictives (import multiple, suppression, attente, erreur et relance, prix modifiable, enregistrement direct avec trois photos). Les tests de caméra couvrent les prises successives, le remplacement d’une vue, la limite, l’arrêt du flux et une autorisation tardive. La capture physique reste à vérifier sur téléphone : l’aperçu HTTP interne ne fournit pas l’accès caméra, réservé aux contextes sécurisés. L’appel réel facturé avec le secret de production nécessite une session ChatGPT du propriétaire ; la session du navigateur de développement n’est pas connectée au site.

Le bouton Enregistrer et continuer crée directement une entrée individuelle au tri, sans repasser par un second formulaire. Zone et provenance sont réglables dans un volet ; la fiche complète reste accessible. L’état visuel proposé est stocké séparément du fonctionnement (non testé par défaut pour l’électrique). Les hypothèses par champ et la confirmation de l’opérateur sont conservées. Aucun objet n’est rendu prêt à la vente par l’analyse photo. La vérification navigateur couvre le gril et le textile avec des réponses de fournisseur explicitement fictives ; elle ne valide pas la justesse d’une reconnaissance réelle avec Eden AI.

## Raccourcis clavier

Sur Mac, Commande K ouvre et cible la recherche ; Commande Entrée enregistre et continue la réception (fiche photo ou saisie manuelle visible). Sur Windows/Linux, utiliser Control K et Control Entrée. Les anciens raccourcis de recherche restent reconnus. Les indices sont masqués sur un appareil tactile sans pointeur fin et apparaissent lors de l’usage d’un clavier. Les combinaisons Mac sont couvertes par des tests de dispatch ; le parcours de focus Control K a été vérifié dans Chrome Linux. Un clavier Mac physique n’était pas disponible dans l’aperçu.

## Réception mobile et étiquettes

Le code EAN/UPC/ISBN est cherché localement sur les photos d’origine avec BarcodeDetector ou ZXing, avant réduction pour l’IA. Les chiffres de contrôle sont vérifiés. Un seul code lisible complète le champ ; plusieurs codes imposent un choix. L’IA peut aussi lire un identifiant explicitement imprimé sur une étiquette, avec statut observé et contrôle de validité. Un numéro de série ou un code incertain n’est pas converti en EAN. Le champ reste vide si rien n’est lisible. Le champ est visible en tête de fiche et dans la saisie manuelle.

Le bouton Estimer le prix reste indépendant de l’analyse. Le tarif est prérempli s’il existe au moins deux comparables retenus et n’écrase pas un montant saisi par l’opérateur. Une référence marque/modèle peut correspondre même si le code-barres n’est pas répété dans l’extrait. L’état non précisé d’une annonce d’occasion est signalé plutôt qu’inventé ; les annonces neuves, les lots et les accessoires seuls restent écartés. Les messages d’erreur de recherche sont affichés près du prix. Les sources et limites restent consultables.

Sur mobile, le bouton d’enregistrement reste accessible au-dessus de la navigation ; l’activité récente est repliée pour laisser la place à la saisie. Une caméra active bloque l’actualisation automatique de l’écran lors d’une modification de l’espace par une autre personne.

Validation mobile : interface vérifiée à 390 et 820 pixels de largeur, prises successives/zoom/changement de caméra/suppression avec flux caméra simulé. Un vrai symbole EAN généré pour le test a été décodé localement, transféré à la fiche puis enregistré avec le prix proposé et les photos. Le scénario de prix utilise des réponses de recherche simulées à deux annonces, sans état indiqué, et contrôle l’erreur de quota puis la reprise. Les appels facturés de production et les particularités d’un téléphone réel ne sont pas validés par ces essais.
